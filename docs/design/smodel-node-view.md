# 软件模式「节点视图」设计方案

- **状态**：✅ 已确认（2026-11-16），实施中
- **涉及**：`src/app/model/smodel.tsx` 的 `NodeViewTab`、新增 `src/components/smodel-node-view/`
- **日期**：2026-11-16

## 0. 已确认的决策

| 决策点 | 结论 |
|---|---|
| 方案 | **A 全量概览图**（模式 → 展厅 → 展区 → 展项 → 绑定） |
| 后端 | **增加 `all=1` 参数**（按模式一次取全部绑定） |
| 编辑交互 | **右侧 Drawer** |

实施中另外确定的两点（受后端能力限制）：

| 决策点 | 结论 | 原因 |
|---|---|---|
| 「命令」是否单独成节点 | **并入绑定节点**（第二行显示），节点类型 6 → 5 | 否则节点数翻倍，图过宽 |
| 绑定「编辑」的范围 | **仅延时**（类型/绑定对象/命令不可改） | `/smodelbind/update` 只接受 `{id, delay}`，改绑只能删除后重建 |

## 1. 现状

`smodel.tsx` 的「节点视图」是一个空壳：

```tsx
// smodel.tsx:87-94
function NodeViewTab() {
    return (
        <div className="w-full h-full flex">
            {/* <SmodelFlow controlData={modelData}/> */}
        </div>
    );
}
```

而 `src/components/SmodelFlow/` 里那个组件**并不是为软件模式写的**——它是
`ContentControlFlow` 的克隆：读的是 `controlData.c_control`，保存走
`updateContentControl`（内容表的控制流程 JSON），`ModelNode` 也只是把标题改成
「前端显示按钮」的空壳。**所以它不能直接接上来，需要重新设计数据层。**

`code.tsx` 式的「表格视图」已经完整可用（展项树 + 模式列表 + 绑定表），
所以节点视图要回答的是表格视图回答不了的问题，否则就是重复劳动。

## 2. 领域模型（真实字段）

### 软件模式 `Software_Model_Info`

| 字段 | 说明 |
|---|---|
| `name` / `msg` / `note` | 名称 / 介绍 / 备注 |
| `current` | 是否为当前模式（1 是 / 2 否） |
| `status` | 1 正常 / 2 停用 |
| `icon` / `sort` | 图标 / 排序 |

### 绑定 `Software_Model_Control`（表格里的「绑定」）

| 字段 | 说明 |
|---|---|
| `model` | 所属软件模式 |
| `pavilion` | 所属展厅 |
| `exhibition` | 所属展项，**可为空** |
| `type` | 1 绑定内容 / 2 绑定设备 |
| `content` | type=1 时：内容 id（`0` 表示「全局内容绑定」） |
| `device` | type=2 时：设备 id |
| `code` | 命令 id：type=1 → 内容控制命令 `C_Control`；type=2 → 设备命令 `Device_Code` |
| `delay` | 命令发送延时（毫秒） |

**两种作用域**（这是节点视图必须表达清楚的）：

- **展项级**：`exhibition` 有值 → 绑定挂在某个展项上
- **展厅级 / 全局**：`exhibition` 为空 → 挂在展厅上（界面上通过展项树里的
  「展厅设备」圆点按钮进入），此时 type=1 的 `bind` 固定为「全局内容绑定」

**两种绑定类型**决定 `bind` 与 `code` 的语义完全不同：

| type | bind（绑定对象） | code（命令） |
|---|---|---|
| 1 绑定内容 | 内容 `C_Info`（或 0=全局） | 该展项的内容控制命令 `C_Control` |
| 2 绑定设备 | 设备 `M_Device`（按 area/link 过滤） | 该设备的命令 `Device_Code` |

### 列表接口返回结构

`GET /smodelbind/list?model_id&pavilion_id&exhibition_id`

```json
{
  "id": 12,
  "model":     { "id": 3, "name": "日常模式" },
  "pavilion":  { "id": 1, "name": "一号展厅" },
  "exhibition":{ "id": 7, "name": "序厅" },     // 展厅级时为 null
  "type": 1,
  "bind": { "id": 21, "name": "宣传片" },
  "code": { "id": 5, "name": "播放", "ip": "192.168.1.20",
            "format": "字符串", "protocal": "TCP Client",
            "port": 10023, "code": "play" },   // 未配置命令时为 null
  "delay": 0
}
```

## 3. 关键约束（决定方案可行性的部分）

1. **接口必须带三个参数**：`model_id`、`pavilion_id`、`exhibition_id`。
   后端实现是 `filter(model_id=..., pavilion_id=..., exhibition_id=...)`，
   不传 `exhibition_id` 时 Django 会按 `IS NULL` 处理，只会返回「展厅级」绑定。
   → **一次请求只能拿到「一个模式 × 一个展厅 × 一个展项」的绑定**。
2. 想画「一个模式下的全部绑定」，要么按展项逐个请求（N 次），
   要么让后端加一个「按模式取全部」的参数（建议加 `all=1` 或让两个 id 可选）。
3. 展项树有现成接口 `getExhibitTree()`（展厅→展区→展项），一次请求即可。

---

## 4. 三种呈现方案

### 方案 A：模式绑定全量概览图（推荐）

**画什么**：以「当前软件模式」为根，向下展开 展厅 → 展区 → 展项 → 绑定 → 命令。

```
┌────────────┐
│ 日常模式    │  ← 根节点（当前模式高亮）
└─────┬──────┘
      ├── 一号展厅 ── 序厅 ──┬── [内容] 宣传片 ── 播放(TCP/10023)
      │                       └── [设备] 投影机1 ── 开机(字符串)
      ├── 二号展厅 ── 展区A ── 展项A1 ── （无绑定）      ← 灰色虚线，一眼看出缺口
      └── 三号展厅 ── 展厅级绑定 ── [内容] 全局内容 ── 播放
```

**为什么这样画**：表格视图是「先选展项、再看绑定」的漏斗，无法回答
「这个模式下哪些展项还没配」「整个展厅的绑定链路长什么样」。
概览图正好补这个缺口，也是"节点视图"相对表格的真正价值。

**数据**：
- 展项树：`getExhibitTree()`（1 次）
- 绑定：按展项并行 `getSmodelBindList({ model_id, pavilion_id, exhibition_id })`
  （N 次，N = 展项数；一般展厅 10–50 个，可接受，且可缓存）
- 建议后端加 `all=1` 参数后降为 1 次（见第 7 节）

**交互**：
- 顶部工具条：模式选择器 + 搜索 +「只看未绑定」开关
- 点击绑定节点 → 右侧 Drawer 编辑（类型 / 绑定对象 / 命令 / 延时），保存后**局部更新该节点**，不整图重载
- 绑定节点右键 → 编辑 / 删除；展项节点右键 → 新增绑定（自动带入 mode/pavilion/exhibit）
- 未绑定展项：灰色虚线边框；绑定了但 `code` 为 null：红色虚线边 + 「未配置命令」角标
- 空态：该模式无任何绑定时，居中提示 + 「新增绑定」

**优点**：信息密度高、能发现缺口、与主画布视觉语言一致（xyflow + dagre）
**缺点**：首屏 N 次请求；图会比较大（需要折叠/搜索）

---

### 方案 B：单展项「绑定链路图」（最小实现）

**画什么**：只画当前选中展项的绑定链路：`模式 → 展项 → 绑定 → 命令`。

**数据**：1 次请求（现有接口直接可用，**零后端改动**）

**优点**：实现最快（约 0.5–1 天），不依赖后端
**缺点**：信息量与表格视图接近，只是换了种呈现；「节点视图」的价值不明显

---

### 方案 C：模式 × 展项 矩阵（不是节点图）

**画什么**：行 = 展项，列 = 模式，单元格 = 绑定摘要（内容名 / 设备名），点击进入编辑。

**数据**：需要「所有模式的绑定」→ 必须后端改造（按模式批量取）

**优点**：横向对比多个模式最直观，适合"切换模式前先看差异"
**缺点**：不是节点视图；单元格信息量有限；需要后端支持

---

## 5. 推荐

**一期做方案 A，但用「N 次并行请求」落地，不阻塞在后端改造上。**

理由：
1. 只有 A 提供了表格视图给不了的信息（全局缺口 + 链路完整性）；
2. B 与表格视图重复度高，做完用户大概率还是回表格；
3. C 偏离"节点视图"的定位，且同样依赖后端。

如果后端愿意加一个 `all=1` 参数，A 的首屏请求数可从 N 降到 1，
建议在二期一起做（改动很小：`if request.GET.get('all'): 不按 pavilion/exhibition 过滤`）。

## 6. 方案 A 的详细设计

### 6.1 页面结构

```
┌──────────────────────────────────────────────────────────────┐
│ [模式 ▾ 日常模式]  [🔍 搜索展项/内容/命令]  [ ] 只看未绑定      │
├──────────────────────────────────────────────────────────────┤
│                                                              │
│   模式 ── 展厅 ── 展区 ── 展项 ── 绑定 ── 命令                │
│                                                              │
│   （xyflow 画布，dagre 分层布局，方向 LR，可折叠展厅）          │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

- 保留现有 Tabs（节点视图 / 表格视图），两个视图共享「当前模式」状态
- 节点视图内部不再重复放展项树（画布本身就是树），但保留模式选择器

### 6.2 节点类型

| 节点 | 颜色/图标 | 展示内容 | 可折叠 |
|---|---|---|---|
| 模式 | 深色 | 模式名、当前模式徽标 | 否（根） |
| 展厅 | 蓝 | 展厅名、绑定数 | 是 |
| 展区 | 蓝灰 | 展区名 | 是 |
| 展项 | 青 | 展项名、IP、绑定数 | 是 |
| 绑定 | 内容=琥珀 / 设备=绿 | 绑定对象名、类型、延时 | — |
| 命令 | 灰 | 命令名、协议/端口/格式 | — |

### 6.3 边与状态

- 实线：正常绑定
- 红色虚线：`code === null`（绑定了对象但没配命令）
- 灰色虚线：展项未绑定（不画绑定节点，只把展项节点置灰）
- 边上标注：`delay`（有延时时显示 `+300ms`）

### 6.4 交互

| 操作 | 行为 |
|---|---|
| 点击绑定节点 | 右侧 Drawer：编辑类型 / 绑定对象 / 命令 / 延时 |
| 绑定节点右键 | 编辑、删除 |
| 展项节点右键 | 新增绑定（带入当前模式、展厅、展项） |
| 展厅节点右键 | 新增展厅级绑定 |
| 搜索 | 高亮匹配节点并「定位」（复用主画布 `ExhibitionFlow` 的搜索实现） |
| 只看未绑定 | 隐藏已绑定的展项，只留缺口 |
| 保存 | 局部更新该绑定节点（不重载整图，避免闪烁——与主画布第九批的做法一致） |

### 6.5 与表格视图的分工

| | 节点视图 | 表格视图 |
|---|---|---|
| 主要用途 | 看全局、找缺口、看链路 | 精确编辑、批量录入 |
| 数据范围 | 当前模式的全部展厅/展项 | 当前模式 × 当前展项 |
| 编辑方式 | 点节点 → Drawer | 行内按钮 → Dialog |
| 保留原因 | 互补，不互相替代 | 已有，不动 |

## 7. 接口清单

**现有即可用**：

| 用途 | 接口 |
|---|---|
| 模式列表 | `GET /smodel/list` |
| 展项树 | `GET /exhibition/tree` |
| 绑定列表 | `GET /smodelbind/list?model_id&pavilion_id&exhibition_id` |
| 新增绑定 | `POST /smodelbind/add` |
| 修改绑定 | `PUT /smodelbind/update` |
| 删除绑定 | `DELETE /smodelbind/delete/<id>` |
| 内容列表（选绑定对象） | `GET /content/list?e_id=` |
| 设备列表（选绑定对象） | `GET /device/list?area=&link=` |
| 命令列表 | `GET /control/list?e_id=` / `GET /code/list?device=` |

**建议后端新增（二期，可选）**：

```
GET /smodelbind/list?model_id=3&all=1
→ 返回该模式下全部绑定（不按 pavilion/exhibition 过滤）
```

改动量：`SModelBindViewSet.list` 加一个分支，约 5 行。

## 8. 工作量估算

| 阶段 | 内容 | 估时 |
|---|---|---|
| 一期 | 画布骨架（复用 xyflow + dagre 分层）、6 类节点、N 次并行取数、搜索/定位、未绑定与无命令的状态表达 | 1.5–2 天 |
| 一期 | 绑定 Drawer（新增/编辑/删除/延时，复用表格视图的表单逻辑） | 0.5–1 天 |
| 一期 | 局部更新与空态、错误处理 | 0.5 天 |
| 二期 | 后端 `all=1` + 前端改为单请求 + 折叠/懒加载优化 | 0.5 天 |

**风险**：
- 展项多时首屏 N 次请求（可加并发上限与缓存，或提前做后端 `all=1`）
- 大图性能（节点 > 300 时需要折叠/懒加载）
- 绑定表单的联动逻辑（type → 绑定对象 → 命令）在表格视图里是内联在组件里的，
  抽出来复用时要注意不要改变现有行为
