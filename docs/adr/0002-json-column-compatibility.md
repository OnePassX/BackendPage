# ADR-0002：现有磁盘 JSON 只做往返兼容，不统一 `c_control` 与 `e_link` 的形状

- **状态**：Accepted
- **日期**：2026-10-21
- **相关**：ADR-0001、架构评审候选 02（flow canvas）
- **决策者**：项目负责人（在 01+02 组合路线讨论中拍板）

## 背景

两种控制图在磁盘上已经是**不兼容的两种形状**：

- `c_control`（内容控制）：嵌套 `children`，节点带 `content_code` 与 `device_code` 两类指令引用
  （`ContentControlFlow.tsx:185-194`）；
- `e_link`（展项快捷控制）：更扁，只有 `device_code`（`ExhibitionLinkFlow.tsx:114-122`），
  且现有序列化器会**扁平化**——`ExhibitionLinkFlow.tsx:181-210` 建了 `childMap` 却从不挂 children，
  `visited` 守卫是死代码（正确实现见 `ContentControlFlow.tsx:259-289`）。

这些列由后端持有，同时被前端大屏与现场设备消费。前端无法单方面改变契约；统一形状需要后端、
大屏、设备端同时配合。

## 决策

**Phase 1 只做往返兼容，不改变磁盘形状。**

1. document adapter 必须能读取两种形状的既有数据（含已被扁平化产出的 `e_link`），
   并在没有用户编辑的情况下**原样写出**（round-trip）。
2. 兼容性验收口径：取真实样本，`serialize(parse(json))` 与原文在**业务语义上相等**；
   键顺序与空白不参与比较。具体比较器在 Step 2 与测试一起定。
3. **不做**形状迁移、**不做**自动升级、**不**在写回时顺手“修正”已有数据。
4. `pme.tsx` 现有的「link JSON 与指令码列表合并」逻辑仍留在域侧，不进入 canvas。

## 被否决的替代方案

| 方案 | 否决理由 |
|---|---|
| **现在统一两种形状** | 需要后端 + 大屏 + 设备端协同；前端单方面改会产出设备端读不懂的数据，属于跨团队变更而非重构。 |
| **宽松兼容（只保证新代码能读旧数据，写回可变形）** | 会在 adapter 里积累隐性分支，且旧数据一旦被写回就永久改变形状，问题从“两种形状”变成“两种形状 × 两类历史数据”。 |

## 后果

- 短期内 canvas 之上仍存在两个 document adapter 与两种字段形状；这是**有意的**，不是遗漏。
- adapter 的 round-trip 测试是 Phase 1 的验收门禁；需要从真实环境取 2–3 份样本
  （至少一份嵌套 `c_control`、一份扁平化 `e_link`）作为 fixture。
- 如果未来要统一形状：需要后端支持数据迁移 + 大屏与设备端升级，另起 ADR，本文不构成障碍。
- 与 ADR-0001 一致：字段映射在域侧，因此「是否统一」是一个域侧可替换的问题，不影响 canvas。
